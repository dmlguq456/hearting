# Model Configuration

Portable model roles and profiles describe work quality and budget; each adapter maps them to its runtime. The shipped `adapters/<harness>/config/models.conf` is copied once to `<runtime-home>/agent-config/models.conf`. That copy is user-owned. A consumer selects a valid complete user file as one unit, or the shipped file as one unit. It never merges the files. When only the optional balanced profile is absent, consumers derive it in memory from that user's light operating point. They do not write the derived value back. Native runtime settings remain separate.

Registry model provenance has one writer: resolved model settings supply the
single `model_source` field, including diversity selection, while profile
receipts supply their selection observations. Dead-attempt settlement can
collapse identical repeated `model_source` provenance in legacy rows without
changing its meaning. Conflicting values, other duplicated immutable fields,
and completion-seal writes retain their refusal. Reconciliation reports
terminal metadata write failures separately from process revalidation.

## Common context operating budget

`CFG_MODEL_CONTEXT_WINDOW` is an optional scalar shared by every model profile, role, and explicit model choice. If it is absent, Hearting resolves it in memory as `800000`; the accepted decimal range is `100000` through `1000000` inclusive. Older complete user files remain selected as a whole when they omit this key. The shipped files declare the default (`800000` for Claude and OpenCode, `1000000` for Codex, which Codex itself caps at the selected model's `max_context_window`), while seed-once installation leaves existing user files byte-for-byte unchanged.

The value is a requested operating budget, not a statement about the model service's maximum. Activation/update/refresh and a successful `hearting model set <harness> context-window <tokens>` project the resolved scalar into Claude's `CLAUDE_CODE_AUTO_COMPACT_WINDOW` setting and Codex's root `model_context_window` config key. Projection updates that managed value in place, preserving unrelated settings; Codex table values do not replace the root projection. A no-op scalar edit also repairs native drift. `--dry-run` writes no files. Activation records the original native value and the value it last projected. Deactivation restores or removes that key only while it still equals the recorded projection, preserving later user edits and unrelated settings. Legacy activation records without a baseline keep the native key because its ownership is unknown. `hearting model set` does not change activation ownership records: a changed value becomes the baseline at the next refresh, while setting the same value already projected by activation cannot be distinguished from leaving it untouched and is restored on deactivation.

These values affect newly created sessions or threads. Existing sessions and threads keep their captured settings; an already running Codex app-server reads the updated root key for each new thread, including threads started through Hearting's native queue, so no daemon restart is needed. OpenCode 1.19.0 applies the budget at runtime startup to catalog models of providers it loads, lowering `limit.context` and, when present, `limit.input` while preserving smaller limits and output allowances. For OpenCode 2 headless dispatch, Hearting reads the selected model's effective limits with `opencode api --standalone` and the prepared worker environment, caps that model in the native `providers` config, then resolves the model again with the capped config and the same worktree location. Each API command owns a short-lived private server; its PID is not reported as the later worker's identity. The actual `opencode run --standalone` worker receives the same final `OPENCODE_CONFIG_CONTENT`, selected model/provider/variant, worktree, and native permissions. The receipt binds this launch to the config hash and worktree location, while the shared user service remains untouched. A missing, changed, or over-cap model remains a launch error. The V2 API snapshot may precede plugin settlement, so an unavailable model is not replaced with a guessed catalog value. The V1 compaction calculation is limited to the tested 1.19.0 consumer; V2 limit observation does not establish V2 compaction behavior. Model capacity, output reserve, disabled compaction, and service behavior can still reduce the usable operating window. Hearting does not claim that the requested value was behaviorally measured.

Use `hearting model set <harness> context-window <tokens>` to change the user-owned scalar and `hearting model get <harness> context-window [--json]` to query its resolved value and source. Queries report the requested/configured value and native application details, not measured effective capacity. These edits affect new launches. A sealed route keeps its depth (and any explicit model pin it sealed), not a model name: every stage launch reads the model for that depth from the current table, so the next stage of a running route starts on the edited value, while a process that is already running finishes on the model it started with.

## Explicit user edits

`hearting model set <harness> <tier|role> <model>[@effort]` makes one explicit edit to the selected user model file. `<harness>` is `claude`, `codex`, or `opencode`. A missing user file starts from that harness's shipped seed. A present malformed, incomplete, unreadable, unsafe, or non-regular file is preserved and reported; it is never replaced with shipped defaults as a side effect of editing.

Targets use existing declarations and resolvers. A bare name that matches both a tier and another target means the tier. `tier/<name>`, `profile/<name>`, and `role/<name>` disambiguate when needed. Existing roles alias their configured shared tier: editing a role updates that tier for every consumer of it. It does not create a per-role override. A profile target updates only that profile's direct-model declaration, keeping its current resolved budget when the suffix is omitted. If the requested target is the previously absent balanced profile, only that requested profile is materialized from the existing balanced resolver's user-derived budget. Unrelated edits do not materialize optional profiles.

For tier and role targets, omitting `@effort` preserves the configured tier budget. An explicit suffix updates the runtime's existing budget field (`EFFORT` or `VARIANT`). For profile targets, an omitted suffix preserves that profile's currently resolved budget. Model identifiers are stored as data and are never executed by a shell. The command does not probe a remote runtime or claim that a saved identifier is available in a particular runtime version.

For OpenCode 2, an `@effort` value is the exact runtime variant (`provider/model#variant`), and its allowed set follows the service catalog's per-provider/model `variants` observation. Saving rejects a combination the observation reports as unsupported, and rejects an explicit variant for a model the catalog did not observe. Launch fits the saved request to the observation instead of rejecting it: a provider-less model id takes the catalog's one matching full id (several matches narrow to the one automatic selection admits), and an unsupported variant moves to the highest observed value at or below it on the order `minimal < low < medium < high < xhigh < max`, otherwise the lowest above it. An unobserved model, an unknown observation, and a variant off that order run as requested. The saved settings are never rewritten, and the launch receipt and attempt row record the original request (`model_fit_from`, `variant_fit_from`) beside the effective `model` and `variant`. `runtime-default` and an omitted suffix (which preserves the configured budget) are always allowed, observed or not.

An invalid target or unsupported budget is rejected before user-file mutation. `--dry-run` and byte-identical no-op requests create no config directory, lock, or backup. A real edit validates the complete candidate, preserves other declarations, comments, ordering, line endings, native settings and unrelated user files, writes one exact preimage backup for an existing config, then atomically publishes the candidate under a canonical target lock. Concurrent invocations of this command serialize. The filesystem's final precheck-to-rename interval is not a kernel compare-and-swap against non-cooperating writers; callers report conflicts they observe and do not roll back a later successor.

The command configures future consumer reads. It does not rewrite generated adapter projections, active route seals, or process-local model selections. Use the existing runtime consumer and route policy as the authority for those surfaces.

## Following newer models

Every cell of the user's file that names a model (a depth line `model/<id>:<effort>` or a tier line, including one the user chose by hand with `hearting model set`) follows the newer same-family model of the user's own harness list by default; the user says "keep this one" separately. `hearting update` (all its paths, `--auto` and a pinned channel included) and `harness runtime refresh`/activate do the writing, and so does every path that runs an activation: a managed release's install and the OpenCode install driver's guard refresh. An update touches only the harnesses it handles (the chosen `--runtime`, else the activated ones), never an uninstalled or unchosen one. The session-start hook, stage launch, Fleet, `config status` and `runtime status` never write. A refresh writes before it draws the default agent definitions, so the table and the definitions agree after one refresh. `utilities/model_follow.py` holds the one rule and the one plan (`fleet_view` reads it; the plan and `apply_harness` read the selected file itself, so a cell the file has no line for is no cell, and `apply_harness` applies the same stage functions); each harness's list reader (`tools/fleet/explorer/model_catalog.py`) only turns its list into rows. The list is the one the CLI already received for this account: Hearting never refreshes it, starts a service or calls a model.

**What is newer.** The newest same-family version visible in the account (Codex `upgrade.model` is read first). One pointing at another family, or a price more than double or below half (OpenCode only), is only a proposal and is never written, as is a model marked previous generation, one that needs a newer CLI than the installed one, one whose listed efforts cannot be stored (`minimal`, `none`), and a Claude alias cell or a model the list does not know. The effort stays, or drops to the value just below when the new model lacks it (the rule OpenCode applies at launch), and the result line and record say so. The lines that must change with a cell (the failover cascade, OpenCode's automatic fallbacks, and the main-session-only list when the old model is on it) are written in the same one write with the merged value; a cell whose lines cannot all move is not followed at all.

**The record and the state.** A cell's state comes from its value and the one record at the end of its line, nothing else:

| End-of-line record | Value now | State |
|---|---|---|
| none | any | follows (the default) |
| `# auto-follow <date>: A -> B` | B | follows; the last follow, A to B (`(effort was <e>)` when the effort was lowered) |
| same | A | kept: a person went back to the earlier value, so it is not taken to B again |
| same | other | follows: a person chose another model; the record is old and the next write to the line replaces it |
| `# auto-follow keep <date>` | any | kept: it changes only when a person releases it |
| `# auto-follow held <date>: B rejected; back to A` | A | held (B): B is skipped, and a different newer model the list gives is followed |
| two or more records on one line (made by hand) | any | kept: the person's; `... follow` clears them |
| same | other | follows |

A form that is not known, or a broken record, reads as no record. A comment the user wrote on the line stays; a line carries one record. A `held ...: B rejected` on any line of a harness's table makes that harness skip B for every cell.

**Keep and release.** `hearting model set <harness> <target> keep` writes the keep record and leaves the value; `... follow` removes a keep or held record (the value stays; the next update follows again, except to a model the outcome record still holds as refused: that one is skipped for as long as the record has it, whatever the cell's record says, and that line is lifted when the model answers a closed attempt, which choosing that model by hand brings about); on a line with no record it writes nothing. Both take the same lock, backup and `--dry-run` as any edit, and a changed record is never reported as "unchanged". `keep` and `follow` are reserved words here, not model names.

**Going back.** When a registry close confirms that a model was refused (the per-model `unavailable` record of `utilities/model_outcome_record.py`), the cells of that harness whose value is that model and whose record reads `A -> that model` go back to A and read `held ...: that model rejected; back to A`, so the next retry starts on A. Their companion lines go back only when the line's own record reads a follow to that model (the person's own lines, which carry none, stay), and the result line says each item that moved (`cascade <B>:<e> -> <A>:<e>`). One record per line cannot tell apart two cells that followed to one model from different earlier values and share a line; such a line goes back to the earlier value of the cell that goes back. That is a known limit. This is best effort inside the close's one wait: it never changes the close's result, order or time, it opens the table only when a refusal was confirmed, and a table it cannot lock in time is left for the next update or refresh, which goes back first and then follows. A cell the user set to that model by hand has no earlier value in a record, so it stays. Ends that are not refusals (capacity, limits, authentication, a transient error, a dead process) never go back. A pass also goes back to the same effect for a refusal the close did not get to, and it never follows to a model the record shows refused, so one update never follows a cell and takes it back. OpenCode's record is its usage cache: only a model-level reason (`model-not-found`, `model-unavailable`) counts, for every line of the cache and for the account in use (a line of another credential generation or account is unknown); the authentication and subscription reasons (`credential-expired`, `authentication-rejected`, `subscription-missing`) are not refusals of a model. OpenCode does not go back at the close: the next update or refresh does.

**Writing.** Only through the table's edit path (lock, `.bak` before the edit, whole-file re-validation, comments kept, a later writer is preserved). Each cell is written whole or not at all, a line that is not changed keeps its bytes, and a second run changes nothing. Any failure (unreadable list, unwritable file, lock, rejected re-validation) is one line and never fails the update or refresh. A pass waits for the table's lock one second at most (an activation holds locks of its own paths, so a longer wait could meet `hearting model set <harness> context-window`): a table locked longer is not written (`table not updated (lock-timeout ...)`) and the next update or refresh does it. A table the person made read-only (no write permission) is not written on its own either, and is said once when there was something to write: `model follow: <harness> table is read-only · not updated` (`hearting model set` still writes it, as before). A pass or a close for one harness reads only that harness's own table: `HEARTING_MODEL_CONFIG_HOME`, which pins one harness's home, is not read for another's. A result line is `model follow: <harness> <target> A -> B (<effort>[, was <e>]) · backup <name>`, `... back to A · B rejected`, or `proposal ...`, followed by one line that the models the field weights were measured on may differ from the table now. `harness config status` adds `newer n`, `proposal n`, `followed n`, `kept n`, `held n` to a models.conf reading (zero counts are not written). A CLI-too-old note appears only from local facts (Codex: the list's `client_version` equals the installed CLI, the table's model is marked previous generation, and no newer same-family model is listed; Claude: a listed model needs a newer CLI), never from the network.

## Shipped-default-only maintenance

A change that touches only the shipped default stays separate from the user-owned actual model set: edit `adapters/<harness>/config/models.conf`, then finish through the normal generation and existing fixture path as small `direct` work. It does not pick new concrete default values on its own, does not sync provider or user config, and does not clean up model-name literals across the repo.
