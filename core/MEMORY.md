# Memory — Unified Store (canonical)

> Split from `CONVENTIONS.md` on 2026-06-23. Memory is an independent subsystem. Preserve the §7 numbering. This is the single source; the spec is `<artifact-root>/spec/prd.md` (artifact root: `CONVENTIONS.md §5.1`), and the implementation is `tools/memory/mem.py` plus the dependency-free `protocol_v2.py`, `sync_v2.py`, `git_exchange_v2.py`, and `migration_v2.py` modules.

## §7. Unified Memory System

> Three former memory surfaces—short-lived post-its, durable learned memory, and the global user profile—share **one portable store**. The store is infrastructure, not a semantic policy engine. **The agent decides contextually what is worth storing, retrieving, promoting, merging, or pruning.** Deterministic code owns only mechanical concerns such as schema validity, scope isolation, lifecycle execution, pending protection, bounded I/O, telemetry, and recovery. Behavioral rules belong in the runtime bootstrap, `CONVENTIONS`, `WORKFLOW`, or Skills rather than memory.

### §7.0. Store Architecture

- **Store:** each server owns one local SQLite WAL source of serving truth at `${XDG_DATA_HOME:-$HOME/.local/share}/hearting/memory/memory.db`; an existing `<agent-home>/memory` store remains a compatibility location. The database, WAL/SHM, replica identity, locks, peer watermarks, and FTS/CJK/capsule/topic indexes stay local and are never exchanged through Git. Schema v7 adds the retrieval capsule (`headline`, `aliases`, `entities`, `topics`, `artifact_refs`, `canonical_id`) and temporal state (`status=active|superseded`, `superseded_by`) beside the original body. The normalized topic table and search indexes are derived and rebuildable.
- **Tier and scope:** the DB is the sole source of truth; file surfaces are on-demand views.

  | Channel | Store tier/scope | Synchronization |
  |---|---|---|
  | `mem note` / `mem add` working-tier records | working/project | `mem note` or `mem add` → background exchange after the write |
  | `projects/<cwd>/memory/`, built-in file memory (disabled per adapter where the runtime supports it, e.g. Claude's top-level `autoMemoryEnabled: false`) | durable/project | not absorbed by routine `mem sync` (D-79); an explicit `mem migrate --all-projects` remains the one-time recovery/import path for files left by a prior enabled period |
  | DB records with `type=profile`, the cross-project profile source of truth | durable/global | `analyze-user` → `mem add` → background exchange after the write; `user_profile/*.md` is an on-demand `mem export` cache for human reading, not a source of truth |

- **Remote convergence:** Git carries only deterministic immutable v2 operations under `protocol/v2/ops/<prefix>/<op_id>.json`. It never carries a live database, WAL, mutable append log, or correctness-bearing dump. The logical shared state is the pure fold of the complete validated operation set; arrival order, Git topology, batch order, and wall clock are not semantic precedence. Routine synchronization uses a private dedicated exchange path outside every project tree and local configuration root, disables repository hooks and attributes/filter behavior, and stages only allowlisted protocol objects. The home directory is not itself such a project tree even when a session was opened there: it is an ancestor of every default runtime path, so counting it would exclude the shipped exchange location from itself and leave no usable default. Its descendants remain eligible, and a home that genuinely is synchronized needs an explicit exchange path outside it. It never runs from that checkout as an agent instruction-discovery directory and never creates or edits project rules, skills, hooks, settings, ignores, or attributes. Access recency is server-local: reading a record moves its local `last_accessed` and authors no operation, so an operation's prior and post state carry the value that record's own lineage already states rather than the live row's. Digesting the live row instead made a destructive operation's prior evidence unmatchable for any record anyone had read since it was last written, blocking that operation permanently and stalling the whole store's convergence (2026-08-21 field failure).
- **Repository rename:** foreground `mem sync`, the existing `reattribute`
  command, and eligible routine exchange follow a GitHub rename only when the
  old and current remotes resolve to the same numeric repository ID and the
  current canonical name. The caller passes its normalized `project_key` into
  the detached worker; the worker's store-directory cwd is never treated as
  the caller's project. Before writing, the normal operation takes a
  consistent local DB backup. One transactional v2 `rekey` moves the project's
  records and serving frontiers, preserving IDs, bodies, pending obligations
  and immutable history. The logical operation namespace stays stable;
  schema-minor 1 carries the serving namespace in `provenance.source`,
  including subsequent writes and new records. Subsequent writes depend on
  the successful rename object; conflicts remain visible across its addresses
  and normal resolution and restore use the serving address. Unsettled
  frontiers leave the rename pending while ordinary sync continues. Older
  readers quarantine these operations and retain their prior projection;
  updated replicas fold the same immutable objects without rewriting old
  ones. Missing or inconclusive repository evidence leaves records untouched
  and the caller intent available for a later eligible exchange.

  Each automatic migration records a versioned identity and exact batch
  coverage in the existing immutable `rekey` operations. The existing
  `reattribute --undo <migration-id>` path authors inverse `rekey` operations
  for only that migration's moved IDs. It preserves unrelated destination
  writes and refuses the whole undo if any moved record has changed since the
  migration. Repeating apply or undo is idempotent. An applied undo suppresses
  immediate automatic reapplication for that repository address pair; an
  explicit `reattribute <id>` remains available to deliberately apply it
  again. Missing evidence or unsettled frontiers cause no data mutation and
  remain eligible for retry. No rename alias, required flag, extra
  confirmation or direct DB edit is needed.
- **Compatibility dump:** `dump.jsonl` is a stable ID-sorted v1-compatible materialized projection for old readers and limited compatibility import/export. It is not a convergence input, is never pushed or destructively imported by routine v2 sync, and cannot by itself recover v2 frontiers, conflicts, tombstones, quarantine, or unconfirmed outbox state. Complete recovery requires protected immutable v2 objects plus a consistent local backup or a separate lossless v2 bundle.
- **Remote enablement and cutover fence:** `MEM_SYNC_REMOTE=1` is the canonical explicit opt-in. An unset canonical flag with `MEM_DUMP_PUSH=1` selects the same v2 exchange with one bounded deprecation warning; the alias never pushes `dump.jsonl`. With both flags unset or `0`, `mem sync` stays local. Enablement, remote URL, protected ref, and exchange path also resolve from one user-owned cross-runtime policy file at `${XDG_CONFIG_HOME:-$HOME/.config}/hearting/memory-sync.json`, which the process environment overrides field-for-field. Only one adapter keeps a settings file able to carry environment defaults, so policy held there alone would leave the sibling adapters synchronizing local-only; the shared file is the portable surface and grants no authority the flag contract below does not already require. Remote exchange is allowed only when the store is either provably fresh v2 or has a completed sealed seed epoch **and** a v2-only old-writer fence is verifiably active. A nonempty legacy, unseeded, or unfenced store fails closed before render, fold, push, confirmation, or watermark advancement. `mem migration` can execute the checked local phase transitions only with sealed inputs, explicit `--apply`, and a matching `--expect` digest; it never auto-discovers or self-authorizes a live roster, credentials, protected ref, or all-server rollout. Snapshot seed construction includes its complete captured ancestry, binds reservations and seed objects in one immediate transaction, and fails before reservation on a post-snapshot tail or roster namespace mismatch. Snapshot also seals the exact compatibility graveyard bytes; only proven absent-record entries become prior-state plus tombstone seed operations, while absence never implies deletion. Delta drain seals both the exact capture interval and the corresponding delta-seed manifest. Rollback preparation holds a durable writer barrier and accepts only a verified complete bundle containing the protected-ref proof, all active-replica pre-cutover artifacts and phase receipts, immutable object union, unconfirmed set, normalized state sections, and preserved graveyard sources. Export refuses loss. Apply requires a self-digested local target request, a fresh target backup, and an atomic verified projection install; its sealed target/install evidence is crash-retryable. Close imports exactly one canonical apply receipt for every active replica before committing the complete bundle digest and removing old-writer triggers from DB-issued closed evidence. The terminal writer mode remains fenced, so only the verified old v1 path is re-enabled; the current v2 funnel stays fail-closed until a new cutover.
- **Harness integration:** automatic memory lifecycle belongs only to the interactive, user-facing main session (D-42). `mem inject --hook` may expose a bounded working, durable, and profile summary at main SessionStart; adapters whose start event repeats on resume, clear, or compact may keep this opt-in. Each eligible main-session prompt runs a deterministic candidate probe over the active current-project/global capsule index. By default it exposes at most six headline-and-ID candidates within 2,400 UTF-8 bytes; the explicit `MEM_CANDIDATE_BODY=1` opt-in permits the bounded one-candidate short-body exception described below. Candidate lookup does not touch access dates, widen scope, or decide relevance. Nothing runs at session end (D-82). A successful write schedules one background exchange after a 20-second batching window (an in-flight run requests at most one follow-up); a main-session `recall`, `candidates`, or `inject` schedules one read-trigger when the last successful receive is older than ten minutes. Explicit `show`/`recall --no-touch` skips notice consumption and read-trigger work and uses a migration-free read-only snapshot; ordinary main-session `show` and `recall` keep their touch behavior. Worker sessions never trigger the read side, and `MEM_EXCHANGE_AUTO=0` turns both triggers off. Write-triggered exchanges commit the local mirror and apply lifecycle expiry. Read-triggered exchanges only receive/export and skip expiry, migration, index rebuild, and duplicate scans. Remote exchange runs only under the explicit flag contract above; with remote disabled, write-triggered exchanges stop at the local dump commit. A failed run leaves one line for the next foreground command, and unsent changes retry on the next write or read. A candidate is shown once per session and again after compact or `/clear`. There is no automatic distillation agent (D-78): the main session decides what is worth writing and declares exactly one storage purpose — `decision`, `user-correction`, `unresolved-obligation`, or `artifact-pointer`. Artifact-backed knowledge is represented by a pointer and retrieval reason, not a duplicate artifact summary. Registered dispatches, loops, title workers, and native subagents are worker sessions: they never run the prompt candidate probe, inject memory automatically, or start the read-triggered exchange. A unit may declare read-only bootstrap material (`roles/units/_schema.md` `bootstrap:`); the dispatching runtime attaches a bounded set of matching preference bodies once while assembling that worker's prompt through `mem bootstrap-context`, which ranks like `mem candidates` and touches no access date, event log, or receipt. The worker decides whether it applies. Units without a declaration receive nothing (2026-09-30 user direction: worker bootstrap is optimized per unit, and memory is one of its materials). Hook registration remains adapter-native.
- **Worker memory-write boundary (D-42, revised 2026-09-30):** (1) Tidy is main-session/user only, including runtime compaction (see [`capabilities/session-tidy.md`](../capabilities/session-tidy.md)); workers and sub-sessions are excluded. A nonempty automatic Claude/OpenCode summary saved to its own verified seat may use the existing snapshot/clear/continue flow after transcript evidence proves the compacted turn ended (up to three hours). Explicitly automatic Codex remote-V2 compaction may join that flow only after the same-session turn ends; its bounded helper requests a real card from that main session through the verified pane and waits for matching card/enqueue evidence. No remote-V2 summary is fabricated, and token-qualified idle is not turn-end evidence. Manual/unknown compaction, outside-herdr/project seats, changed input/target/card, uncertain sends, and failed card persistence stay queue-only. Idle-origin work remains status-only even if compaction occurs during it; compact-origin continuation keeps its existing behavior. Compact cards preserve their source transcript and any real summary/tail used; the next session receives the card once. (2) An explicitly called tidy worker (`session-tidy`) only emits an action list; a write happens solely through the apply command `mem tidy-apply`, a closed set (add, supersede, reinforce) with no delete, reversible with `mem tidy-undo`. (3) The runtime records a decision itself the moment it receives a direction-confirmation answer. (4) Every other worker writes no memory. (5) Bootstrap material a unit declares is read-only.
- **Session tidy:** the card is server-local runtime state under `${XDG_STATE_HOME:-$HOME/.local/state}/hearting/session-tidy/`, not a memory record. It is not a `post-it handoff` (a pending-delivery DB record) and needs no `mem consume`: one card generation is injected once per seat, to the first qualifying session. `utilities/session_tidy.py` writes the card, queues the detached tidy run, and hands the card to a peer pane. Automatic Claude/OpenCode compact cards retain the complete summary, a bounded tail of recent conversation the summary may not have seen, and the original transcript path; an eligible persisted card can book the existing clear flow after transcript-confirmed turn completion. Explicitly automatic Codex remote-V2 compaction may use that flow after its exact turn ends, by requesting a real card from the same main session through the verified pane and requiring matching card/enqueue evidence; empty summaries and idle signals are insufficient turn-end evidence. Idle-origin work stays status-only through compaction, while compact-origin continuation keeps its existing behavior. `mem tidy-apply` and `mem tidy-undo` are the only memory writes of that run, and they go through the ordinary write path, so they schedule the background exchange like any other write. Each answered question becomes one `type=decision` record in the `working` tier (21-day natural expiry, project scope) with source key `user-choice:<sha256>` of the question and the chosen answer, so the same question and answer is written once; the tidy worker moves a lasting decision to a durable record.
- **Idle tidy:** a main-session Stop/idle event with known latest-request input-context tokens at or above 200,000 may book the existing session-tidy helper after the configured wait (default 3,240 seconds). The optional `session-tidy.json` policy changes idle timing/threshold only; its default wait is an operating choice, not provider-cache evidence. Provider/model/request cache expiry remains `unknown` unless the actual request configuration and expiry are observed. The helper asks the main session to author its own card, queues the ordinary session-tidy action list, then clears once after exact-session, idle-screen and empty-input checks. It does not start another distiller. Its post-clear prompt is status-only; automatic idle tidying rearms only after real user input in the successor. See [`capabilities/session-tidy.md`](../capabilities/session-tidy.md).
- **Recall:** `mem candidates` is a mechanical prompt-time capsule lookup; the acting model ignores unrelated candidates and reads the full record before applying a relevant one. `mem recall` is the explicit deeper search over active capsules followed by body/CJK compatibility indexes, with optional exact `--topic`; historical rows require `--include-superseded`. If the ID is already known, use `mem show <id>`. A successful prompt probe writes a same-turn recall-opportunity receipt even for zero hits. Main-session material mutations require that receipt; a failed/missing hook recovers through an explicit contextual `recall` or `skip` decision in `mem recall-gate`. Registered route-bound workers are exempt because they do not own the main memory lifecycle. Declared unit bootstrap material is not a recall and creates no receipt.
- **CLI:** Core surfaces include `recall-gate`, `topics`, `supersede`, guarded `activate`, `conflicts`, `show-conflict`, and agent-authored `resolve` in addition to the existing record, lifecycle, export/import, and curator commands. `supersede <old> --by <new>` keeps the old row recoverable and removes it from default recall/injection; it never deletes either body. Legacy-source `migrate` is current-project by default and requires `--all-projects` for an explicit cross-project recovery scan. The separate operator-only `migration` namespace owns an existing-store v2 cutover: mutating phases are deterministic dry-runs unless both `--apply` and the current `--expect` state digest are supplied. It uses sealed manifests and contained operator-selected artifact directories; it grants no authority over a live roster, credentials, store, or protected ref by itself. Its one exception is `migration join`, the fresh-store bootstrap: a provably empty store has nothing to snapshot, seed, or prove equal, so joining an existing exchange seals a fresh epoch and activates its writer fence in one checked leaf, deriving a stable epoch from the replica and protected ref so a repeated join is the same join. It refuses any store already holding records or v2 operations, which needs the sealed-seed cutover instead. `sync --json` reports versioned `not-configured|local-only|queued-offline|fetched|folded|conflict|quarantined|push-retry-exhausted|remote-confirmed|hard-failure` status and phase outcomes. Exit 0 means local health plus no unmet remote obligation or warning, exit 1 means local writes remain safe but remote/deferred/conflict/quarantine/retry work remains, and exit 2 means integrity, protocol, path, rewind, writer-fence, or unsafe-migration failure.
- **No automatic periodic curation (D-78):** there is no nightly cron backstop. Where durable tiers drift over their soft ceiling between sessions, cleanup is a one-time manual pass (D-80), run as its own separate cycle rather than an automatic loop.
- **Curator commands under D-18:** `curate-snapshot` exposes active project records and a destructive allowlist. The existing guarded mutations remain, and `supersede` may relate two allowlisted active records without deleting history. Profile, pending-delivery, cross-scope, cross-project, nonexistent, and cyclic relations fail closed. There is no automatic applier: the acting agent (main session, or the manual cleanup cycle under D-80) calls the guarded mutation commands directly.
- **Invariant D-18, D-35, D-40:** the acting agent—main or a manual cleanup pass—makes semantic memory decisions from available context. Scripts may validate action shape, visibility, identity, transaction safety, pending protection, graveyard recovery, and bounded lifecycle mechanics. They must not decide relevance through keyword lists, content categories, confidence thresholds, or fixed phrases. Unconsumed pending handoffs fail closed against destructive operations until an explicit `consume` transition.

### §7.1. Semantic Decisions Belong to the Agent

There is no deterministic promote/skip classifier. The acting agent judges whether a memory operation is useful in context, including whether information is durable, non-obvious, recoverable elsewhere, stale, or merely ephemeral. The four storage-purpose labels are a bounded ingress contract after that semantic judgment, not a keyword classifier: code validates the declared purpose but never infers it from content. Manual user-directed memory remains governed by its owning capability.

### §7.2. Write Mechanics and Deduplication

Tests that accept answers through real workflow code isolate every memory sink
in their shared fixture, including the store, write journal, pending decisions
and remote exchange. Direct suite execution has the same boundary as the test
runner. Proven test records in a user's store use the normal guarded delete and
graveyard restore path; their historical journal is preserved.

The delete command retains known pre-delete content as a bounded event snippet.
Older events whose snippet was never recorded stay unchanged; a display names
that missing content explicitly rather than showing a blank change.

- After deciding to write, inspect visible memory and prefer updating the canonical record over creating an obvious duplicate. Fuzzy similarity is candidate evidence for the agent, not an automatic semantic verdict.
- Prefer artifact pointers over replicated artifact prose. A pointer includes the current artifact path and only enough body text to explain why and when it should be retrieved.
- Populate a concise headline plus bounded aliases, entities, and topics. These form the retrieval capsule and topic index; the full body remains evidence read on demand.
- A manual `mem add` should pass `--headline`/`--alias`/`--entity`/`--topic` explicitly: an empty capsule is not retrievable through capsule-first recall or prompt candidates. `write_record` mechanically extracts file paths, commit hashes, backtick identifiers, and ID-shaped tokens (e.g. `D-40`, `rt-*`) from the body into `entities` as a merge-only, non-semantic safety net (D-40 boundary — extraction, not judgment); it does not replace populating `--headline`/`--alias`/`--topic` by hand. When a write arrives with no capsule fields at all and nothing was mechanically extracted, `mem add`/`mem note` print one advisory stderr line — this never blocks the write.
- Preserve changed decisions with `supersede` so default reads see one active canonical path while historical rows remain auditable.
- After determining that memory is stale, use the guarded remove or merge path so recovery metadata is preserved.
- Every supported semantic mutation goes through one `BEGIN IMMEDIATE` transaction that changes local semantic/graveyard state, allocates the replica counter, creates the exact canonical operation, and queues its transactional outbox row. Local commit is the command's durability boundary: offline or failed remote exchange never rolls it back. An unsupported write path fails closed rather than bypassing the outbox.
- The active replica ID is bound to private local installation evidence outside `memory.db`. A copied/moved database with mismatched evidence is read-diagnosable but cannot author or remotely synchronize until an explicit `mem replica rotate --reason …` creates a new activation boundary; predecessor operations are never rewritten.
- Concurrent variants are preserved in full. A deterministic total key may select a provisional service projection, but it does not resolve semantic conflict. Default injection, candidates, and recall expose only bounded conflict identity/index evidence; `show-conflict` displays every labeled variant and only a new agent-authored `resolve` operation may descend all maximal heads.
- Related records may use `[[name]]` links in the DB `links` column. FTS5 indexing happens mechanically on insert; `MEMORY.md` remains a legacy projection view.
- Code may report capacity pressure and similarity candidates. The curator decides whether and how to consolidate them.

### §7.3. Agent-Backed Mutation Boundary

Purely deterministic monitors may surface candidates but cannot promote, skip, merge, or prune based on semantic rules. A user-directed `mem note` / `mem profile-append` flow or an agent-backed curator pass may perform the mutation. The script then enforces only the mechanical action contract and recovery boundary.

#### D-43 — On-call incident-to-proposal bridge

An agent-backed on-call loop may use bounded recent memory mutation events only
as incident leads. It must read any selected record in full and corroborate the
claim against current source, tests, logs, artifacts, or runtime evidence
before sending it to the offline improvement proposal inbox. Memory remains
unchanged and is never sufficient evidence by itself.

The acting agent chooses one stable incident identity. Deterministic proposal
code may compare that identity exactly, append bounded recurrence evidence
under the inbox lock, and fail closed on ambiguous duplicates; it must not infer
semantic equivalence. A named automated collector may create `observed` and
advance only through `reproduced` to `proposed`. It cannot change a reviewed or
terminal decision, impersonate a human approver, edit source or runtime state,
or activate a realization. This bounded task operation is not automatic memory
lifecycle: the on-call worker does not inject, curate, sync, consume, or mutate
memory, preserving D-42.

### §7.4. Recall — On-Demand Retrieval

`mem inject` may provide a bounded SessionStart summary of active, non-conflicted working, durable, and profile records. On each eligible main prompt, `mem candidates` mechanically searches only the active current-project/global capsule FTS index and exposes at most six headline-and-ID candidates within 2,400 UTF-8 bytes. Unresolved conflicts expose bounded IDs/index evidence, never a provisionally selected body. The agent decides whether any candidate is relevant; a relevant candidate must be read in full before use. Candidate exposure is capsule-only by default; the explicit `MEM_CANDIDATE_BODY=1` opt-in may add one bounded short body for a clearly leading candidate under the existing byte budget. The probe does not treat a lexical hit as adopted truth or touch access dates. Its same-turn receipt proves only that retrieval was not silently omitted. When a prompt hook is unavailable or fails, record `recall` with a focused query or `skip` with a short contextual reason through `mem recall-gate`. Retrieval is information access, not handoff consumption. Bounded telemetry stores query/turn digests, result IDs and counts, output bytes, or the explicit gate decision and later `applied|miss` outcome without storing raw prompts.

| Helper | Purpose | Notes |
|---|---|---|
| `python3 <agent-home>/tools/memory/mem.py candidates <prompt> --session-id <id> [--turn-id <id>] [--hook]` | Expose bounded active capsule candidates and publish a same-turn recall-opportunity receipt. | Main prompt bridges own this mechanical call. Maximum six candidates and 2,400 UTF-8 bytes; no body fallback or access-date touch. |
| `python3 <agent-home>/tools/memory/mem.py recall-gate --decision recall|skip --reason <reason> [--query <query>]` | Record the work-start opportunity decision; `recall` immediately searches active current-project/global memory. | After a hit, use `--outcome applied --gate-id <id> --record-id <id>`; miss uses no record ID. No raw prompt is stored. |
| `tools/memory/recall.sh "<query>" [--full] [--limit 1..100] [--all] [--sessions] [--no-touch]` | Capsule-first FTS5 recall with body/CJK fallback. | Main-session reads update access dates/events by default. `--no-touch` reads a migration-free read-only snapshot without memory/runtime writes. `mem recall` additionally supports `--topic` and explicit `--include-superseded`. |
| `python3 <agent-home>/tools/memory/mem.py show <id> [--all] [--no-touch]` | Print metadata and the exact multiline body for a known ID. | Default visibility is active current project plus global; historical access requires `--include-superseded`. `--no-touch` suppresses access dates, lookup events, notice consumption, and read-trigger work. |
| `python3 <agent-home>/tools/memory/mem.py topics [topic]` | List the active normalized topic index or records under one topic. | This is a navigation index, not an automatic relevance classifier. |
| `tools/memory/index-check.sh [dir] [--fix]` | Check drift in the legacy `MEMORY.md` text index under `projects/<cwd>/memory/`, including missing and orphaned pointers. `--fix` appends missing pointers only. | The built-in FTS5 index in `memory.db` is separately owned by `mem index`. Preserve existing curated lines. |

There are two retrieval surfaces. First, curated memory in durable and working tiers is searched by `mem recall` through SQLite FTS5 with BM25 ranking, falling back to LIKE or `rg`. A shortened or ellipsized snippet is never final evidence: if a hit is truncated or insufficient for the judgment, immediately read its full body by record ID with `show <id> --no-touch` or use `recall --full --limit N --no-touch` for scout work. These no-touch reads use one migration-free read-only snapshot, skip access dates and lookup events, and do not consume exchange notices or start read-trigger work. Ordinary main-session `show` and `recall` keep their default touching behavior. Direct SQLite or `dump.jsonl` queries are not a normal retrieval path. Second, `--sessions` searches raw historical transcripts that have not been distilled into memory. Raw sessions are noisy and should supplement curated memory only when useful.

Database-backed conversation readers keep one read-only transaction across a
chunk's queries. Concurrent appends preserve that view without copying the whole
database. A failed read retains the card and watermarks and reports its cause in
one bounded line.

**Agent-owned adoption:** deterministic candidate exposure prevents the search step from being silently omitted, but the agent alone decides whether prior context may materially improve the current judgment. No fixed signal words, mandatory topic list, prompt classifier, category-to-recall rule, or score threshold may adopt a candidate. Ignore unrelated candidates. Before using a candidate, read its full record; widen to historical, cross-project, body, or raw-session data only when useful, and cross-check retrieved claims against current code or artifacts because memory can be stale.

- **Pointer follow-through:** when a recall result names a project file or
  artifact path relevant to the task, read that current target before using
  the memory claim to report project state. Memory supplies continuity and
  navigation; the referenced artifact and live code supply current facts. A
  missing or changed target is evidence that the memory pointer may be stale,
  not a reason to substitute the remembered summary for the file.
- **Inline recall:** for a simple agent-chosen search, run `tools/memory/recall.sh "<query>"` directly for one or two queries. If a hit needs context, follow with `mem show <id>` or `recall --full --limit N`.
- **Memory-scout capability:** use this read-only capability for deep searches across raw sessions, multiple query angles, many full bodies, or multiple working directories. Start with narrow recall and useful synonyms in any relevant language; inspect hit IDs through `show` or a few full results; widen to `--all` on a miss, then to raw sessions; finish with one line cross-checking live code. Do not bypass the interface through direct DB or `dump.jsonl` reads. Return at most 15 lines: verdict—present, absent, or ambiguous—up to three key quotations, record IDs, and one application instruction. All writes are forbidden, including `add`, `note`, `consume`, `restore`, `delete`, `reinforce`, `merge`, `prune`, or file edits.

Per-cwd isolation remains the default. Use `--all` only for an explicit cross-project need. A mass `--fix` touches gitignored live user data under `projects/` and therefore belongs in a user-directed flow; automated paths may report missing pointers but not repair them.

### §7.5. Mechanical Scaffold — Retrieval, Curation Candidates, and Pending Protection

Deterministic code may detect mechanical conditions and expose candidates around lifecycle operations; the deep curator decides semantic actions. Scripts execute only validated actions under D-18 and D-40.

**D-40 agent-owned semantic memory judgment, superseding the automatic portions of D-15 and D-34:**

- Prompt-submit bridges run a bounded capsule-only candidate probe for every eligible main prompt. They do not run a semantic classifier or inject score-threshold-qualified truth. Candidate bodies remain off by default; the explicit bounded opt-in is defined in §7.4.
- `mem candidates` owns only tokenization, active/current-project-or-global scope fences, ranking, and output limits. At most six headline-and-ID candidates and 2,400 UTF-8 bytes are exposed; no hit is an adoption decision.
- `mem bootstrap-context` owns only the same tokenization, scope fences, ranking, and output limits for a unit-declared topic; it returns at most four bodies within 6,144 bytes, reads the database read-only, and decides no adoption.
- `mem recall` and `tools/memory/recall.sh` remain explicit deeper retrieval tools. `mem recall-gate` is the recovery path when a prompt probe is unavailable and may record a contextual `recall` or `skip`; neither path classifies the prompt deterministically.
- `mem recall --auto` remains retired. `hooks/mem-recall-inject.sh` is now the fail-open portable candidate bridge registered by each active runtime adapter.
- `$XDG_STATE_HOME/agent-memory/recall-events.jsonl` remains bounded raw-prompt-free telemetry. `$XDG_STATE_HOME/agent-memory/recall-opportunities/` stores one atomic bounded receipt per hashed session. A search error creates no valid receipt; zero legitimate hits do.
- Main-session material mutations require a current same-turn receipt or an explicit recall-gate recovery receipt. Registered route-bound workers are exempt and continue to skip main-session memory lifecycle. The runtime-side `bootstrap-context` lookup for a declared unit is outside that lifecycle: read-only, bounded, receipt-free.

**D-16 cleanup signals in `mem inject`:** after the existing `mem inject --hook` block, add a `## 🧹 Cleanup signals` section only when nonempty. It may show cwd-scoped durable near-duplicate groups, capacity over `durable > soft_ceiling=80`, and working records within three days of expiration. The section remains inside the SessionStart cap and defaults to two lines. It is read-only and performs no deletes or flag writes. Under D-18 it is informational: main performs no housekeeping automatically. Housekeeping is a manual pass (D-80): read `curate-snapshot` and its signals, then call the guarded mutation commands directly.

**D-35 unconsumed handoff and thread protection:**

- `delivery_state` is `ordinary`, `pending`, or `consumed`. New `type=handoff` records and explicit `--requires-consume` threads are pending. Only `mem consume <id>` performs the normal pending-to-consumed transition. Source upsert and body dedup preserve pending monotonically rather than lowering it through an ordinary rewrite. `show`, recall/full, and inject are non-consuming. When retrieval exposes `[pending:<id>]`, read the full obligation, apply and verify it, then call `mem consume <id>`. A working pending record does not expire before consumption; its 21-day TTL starts over when consumed.
- `curate-snapshot` shows pending records under `PROTECTED PENDING` but excludes them from destructive `IDS:`. `prune`, `delete`, `merge`, and `lifecycle --apply` recheck DB state immediately before execution and fail closed on pending records. A merge containing any pending record aborts entirely without changing strength or deleting anything.
- Deleted records remain in the graveyard with action and canonical metadata and can be restored one at a time through `mem restore <id>`. Automatic consumption is allowed only in narrow pipeline paths that name the handoff ID and prove successful application through artifacts.

### §7.6. User Profiles — Aspect-to-Consumer Matrix

> Moved from `user_profile/README.md` on 2026-06-23 when the mapping document was removed. **Read profiles from the DB** through `mem profile <stem>` or `python3 <agent-home>/tools/memory/mem.py profile <stem>`. This matrix maps agents to aspects; the aspect body source of truth is the durable/global DB record with `type=profile`. This section is the single source for the matrix. `capabilities/analyze-user.md` and every adapter-native `analyze-user` projection must reference it; root `skills/analyze-user/SKILL.md` is only a compatibility reference.

| Stem | Domain | Consumers |
|---|---|---|
| `01_paper_figure_style` | Paper figures, tables, color, fonts, size, and metric grouping | material, design, research for figure citation style, and editorial roles |
| `02_paper_writing_style` | Paper tone, argumentation, and citation | research, editorial, and planning roles |
| `03_presentation_strategy` | Slide structure, narrative flow, visual decisions, and audience adaptation | material for presentations, design, and editorial roles |
| `04_analysis_methodology` | Data and experiment analysis approaches and verification patterns | material, research, planning, implementation for metrics and verification, editorial, and the main agent for analytical replies |
| `05_domain_expertise` | Domain background such as speech, TF DNN, and signal processing, plus terminology preferences | research, material, design, editorial, planning for abbreviations, implementation for identifiers, and the main agent for recognizing user terminology |
| `07_coding_convention` | Project layout, config, prefixes, preferred layers and frameworks, metric sets, logs and checkpoints, seeds and reproducibility, and naming | implementation, planning for code plans, and the main agent during `autopilot-lab` Step 0, `autopilot-spec` Phases 0 and 2, and the four `autopilot-code` principles |

Aspect 06, conversational meta rules, is excluded because the runtime adapter response discipline is its single source and applies only to the main agent; subagents do not speak directly to the user. The `06_collaboration_style` record remains the default collaboration target for `mem profile-append`. Aspect 07 applies only to implementation, planning, and main-agent code work, not editorial wording. Each agent normally consults three to five relevant aspects.

**Update protocol:** profile bodies live in durable/global DB records. Two flows may update them. `/analyze-user <aspect>` scans prior artifacts such as papers, presentations, code, and reports, extracts patterns, and accumulates them with `mem add durable profile --source user-profile:<stem>` during setup, new-material ingestion, or incremental `--mode update`. `mem profile-append <aspect> "<text>"` adds a generally useful pattern discovered in conversation.

**Source-keyed upsert hazard (data loss):** `mem add ... --source user-profile:<stem>` upserts by `(tier, scope, source)` and REPLACES the entire profile body with the payload. Never pass a partial body through raw `mem add` to "append" one item to a profile — everything not in the payload is destroyed. Interactive single-item additions go through `mem profile-append <aspect> "<text>"` (the only safe partial write: it splices under `## 사용자 수동 메모` and upserts the whole body); body rewrites go through `/analyze-user`, which reads the current body via `mem profile <stem>`, splices while preserving `## 사용자 수동 메모`, and only then writes the complete replacement. A replaced body is kept: `mem history <id>` lists it and `--restore N` puts it back.


**Consumption pattern:** at the start of relevant work, an agent reads each aspect through `mem profile <stem>` and treats the body as a default unless the user says otherwise in the current turn. Per-project conventions in `analysis_project/code/experiment_conventions.md` take priority; profiles are the cross-project fallback. For example, a material figure task reads aspects 01, 03, 04, and 05, while a new-library implementation reads project conventions first and then aspects 07, 04, and 05.
