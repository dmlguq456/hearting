If the user first gives a different instruction instead of continuing, skip the summary and follow only that instruction. This guidance survives body truncation within the 2,400-byte injection limit, including bundled memory references; it is absent from late memory-only injections and peer handoff messages. Claude Code, Codex, and OpenCode give the interactive main session a non-blocking notice based on the latest request's input usage: strictly above 500,000 tokens recommends `/session-tidy`, and strictly above 700,000 asks for tidying now. Each threshold is emitted once per native session ID; a jump across both emits the urgent notice once and consumes both. Compaction does not reset these notices. Owners, workers, auxiliary/reviewer sessions, and subagents are excluded. These notices do not change the runtime's compaction policy. Runtime compaction counts as a session tidy invocation by the main session. Each completed summary may be saved to that session's own seat card and queues memory tidying; a shared project fallback seat only queues memory tidying, so one session's compaction never replaces another session's card. Preserve memory tidying under the existing stable operation ID in the durable queue before any card request or clear booking. Queue acceptance is independent of card-request delivery, booking expiry, cancellation, or clear eligibility; retries and normal hook reconciliation reuse that same queue item. Keep its source card generation unchanged. A card can authorize clear only through an exact recorded acceptance relation for its seat, harness, session, claim, operation, queue item, arrival and newly written card. A nonempty automatic Claude or OpenCode summary saved to its own verified seat may use the existing tidy booking. For Codex remote-V2, an explicitly automatic compaction may use that same booking only after the exact main turn is confirmed complete: the bounded helper then sends one claim-bound request through the verified Codex pane, and the main session writes its real card and enqueues the matching operation. No empty or fabricated remote-V2 summary is used. Claude/OpenCode compact bookings and Codex card-request bookings wait for transcript turn-end evidence; idle alone is insufficient, and a compact booking may wait up to three hours. A matching card and durable queue receipt are required before handover snapshot and clear. Compact-origin clear keeps the existing continue behavior. Manual or unknown compaction, failed card persistence, a project fallback/outside-herdr seat, workers or sub-sessions, a changed session/input/card, or an uncertain card-request send never trigger automatic clear. Codex uses the verified pane transport; this does not add native attachment support. Never block or delay compaction to complete tidying. Worker sessions are excluded. An optional idle tidy starts only from a main-session turn-end/idle event with a known latest-request input-context count at or above `idle.min_tokens`; unknown usage and stale or different-session usage are ineligible. The shared policy is `${XDG_CONFIG_HOME:-~/.config}/hearting/session-tidy.json`. When absent it uses `idle.enabled=true`, `idle.wait_seconds=3240`, `idle.min_tokens=200000`, and `idle.cache_margin_seconds=60`; `overrides.<harness>.<provider>` may override those idle fields. Current adapter payloads do not expose a verified request cache expiry, so the configured idle wait is used and `cache_margin_seconds` is recorded but not applied. Provider, auth route and cache TTL remain unknown where configuration/request evidence cannot establish them. This policy does not change provider cache settings or restore automatic distillation. Codex automatic remote-V2 compaction reuses this same request, claim, card, enqueue, and helper progression after transcript-confirmed turn completion; it does not use idle token eligibility or create a second scheduler. An uncertain send is never retried. Any real prompt, busy/unknown target, draft, form, approval, missing token count for idle work, worker session or other-session identity prevents the send or cancels the booking. After an idle clear, the successor receives one short card-status request and waits for the next user input; it does not receive `이어서해` and does not restart work. Compact-origin continuation keeps its existing behavior, and compaction during an idle-origin booking does not change its status-only follow-up. The status reply, its Stop/idle event and duplicate callbacks do not arm another idle tidy. Manual tidy and ordinary compact clear/continue keep their existing behavior. At a shared project fallback seat each session keeps its own card, so one session's card never replaces another's; a different session receives only the seat's newest card, once, and only if it first appeared after that card's author was last active. The main-authored card keeps work in progress, waiting decisions, the next step and related references first. Below those four fields, add '오늘 한 일' (today's work, with PR/version/result pointers) and '사용자 지시' (brief user quotations marked finished, remaining or deferred), within about 90 lines. Write it from the conversation the main session already holds. The calling main session writes its own handoff card and queues the tidy in one tool call (`utilities/session_tidy.py tidy`: the card is written first, and only a written card goes on to the existing `enqueue` and optional `handoff` for the same caller; `card` and `enqueue` stay available separately with the same meaning). A manual tidy therefore costs one tool call and one short closing reply that repeats the command's `say=` line. Automatic idle and compact card requests need no Skill and no tool: their own text asks for one reply whose first and last lines are the request's nonce markers with the card fields between them. An unmarked, cut-off, late or mismatched reply writes no card and books no clear; if the session ran `tidy` itself, the already accepted request is left as it is. `enqueue` returns at once while a detached runner (`utilities/session_tidy_runner.py`) starts one registered memory worker (`ops/session-tidy-memory`), applies its closed `add`/`supersede`/`reinforce` proposal through `mem tidy-apply`, and leaves one result line (with the undo command) for the seat's next session. The runner reads the conversation tail first: the newest unread part of each record goes to the worker, only a successful apply marks that part as read, and an older unread front stays pending for the next tidy; a record that was only partly read says so (`일부만 읽음(범위)`) and is never reported as 'nothing new'. The same run also refreshes the card's '참고할 기억' list (record ids and titles from what the batch really wrote plus the related existing records, at most 8 and 1,200 bytes), which the next session at the seat receives once with the card or, if the tidy ends later, at its next prompt. `handoff <target>` delivers the card to a peer session through `utilities/peer-steward.py prompt` only and reports its typed verdict. There is no required input and no confirmation step; a failure keeps the card and the watermarks unchanged and leaves one warning line, which counts any writes that had landed or may have landed and then carries the undo command. Clearing and continuing are part of the default flow.
