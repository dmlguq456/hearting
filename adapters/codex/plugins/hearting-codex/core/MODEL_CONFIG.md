# Model Configuration

Portable model roles and profiles describe work quality and budget; each adapter maps them to its runtime. The shipped `adapters/<harness>/config/models.conf` is copied once to `<runtime-home>/agent-config/models.conf`. That copy is user-owned. A consumer selects a valid complete user file as one unit, or the shipped file as one unit. It never merges the files. When only the optional balanced profile is absent, consumers derive it in memory from that user's light operating point. They do not write the derived value back. Native runtime settings remain separate.

## Common context operating budget

`CFG_MODEL_CONTEXT_WINDOW` is an optional scalar shared by every model profile, role, and explicit model choice. If it is absent, Hearting resolves it in memory as `800000`; the accepted decimal range is `100000` through `1000000` inclusive. Older complete user files remain selected as a whole when they omit this key. The shipped files declare the default, while seed-once installation leaves existing user files byte-for-byte unchanged.

The value is a requested operating budget, not a statement about the model service's maximum. Activation/update/refresh and a successful `hearting model set <harness> context-window <tokens>` project the resolved scalar into Claude's `CLAUDE_CODE_AUTO_COMPACT_WINDOW` setting and Codex's root `model_context_window` config key. Projection updates that managed value in place, preserving unrelated settings; Codex table values do not replace the root projection. A no-op scalar edit also repairs native drift. `--dry-run` writes no files. Activation records the original native value and the value it last projected. Deactivation restores or removes that key only while it still equals the recorded projection, preserving later user edits and unrelated settings. Legacy activation records without a baseline keep the native key because its ownership is unknown. `hearting model set` does not change activation ownership records: a changed value becomes the baseline at the next refresh, while setting the same value already projected by activation cannot be distinguished from leaving it untouched and is restored on deactivation.

These values affect newly created sessions or threads. Existing sessions and threads keep their captured settings; an already running Codex app-server reads the updated root key for each new thread, including threads started through Hearting's native queue, so no daemon restart is needed. OpenCode 1.19.0 applies the budget at runtime startup to catalog models of providers it loads, lowering `limit.context` and, when present, `limit.input` while preserving smaller limits and output allowances. For OpenCode 2 headless dispatch, Hearting reads the selected model's effective limits with `opencode api --standalone` and the prepared worker environment, caps that model in the native `providers` config, then resolves the model again with the capped config and the same worktree location. Each API command owns a short-lived private server; its PID is not reported as the later worker's identity. The actual `opencode run --standalone` worker receives the same final `OPENCODE_CONFIG_CONTENT`, selected model/provider/variant, worktree, and native permissions. The receipt binds this launch to the config hash and worktree location, while the shared user service remains untouched. A missing, changed, or over-cap model remains a launch error. The V2 API snapshot may precede plugin settlement, so an unavailable model is not replaced with a guessed catalog value. The V1 compaction calculation is limited to the tested 1.19.0 consumer; V2 limit observation does not establish V2 compaction behavior. Model capacity, output reserve, disabled compaction, and service behavior can still reduce the usable operating window. Hearting does not claim that the requested value was behaviorally measured.

Use `hearting model set <harness> context-window <tokens>` to change the user-owned scalar and `hearting model get <harness> context-window [--json]` to query its resolved value and source. Queries report the requested/configured value and native application details, not measured effective capacity. These edits affect new launches; they do not alter sealed routes or running processes.

## Explicit user edits

`hearting model set <harness> <tier|role> <model>[@effort]` makes one explicit edit to the selected user model file. `<harness>` is `claude`, `codex`, or `opencode`. A missing user file starts from that harness's shipped seed. A present malformed, incomplete, unreadable, unsafe, or non-regular file is preserved and reported; it is never replaced with shipped defaults as a side effect of editing.

Targets use existing declarations and resolvers. A bare name that matches both a tier and another target means the tier. `tier/<name>`, `profile/<name>`, and `role/<name>` disambiguate when needed. Existing roles alias their configured shared tier: editing a role updates that tier for every consumer of it. It does not create a per-role override. A profile target updates only that profile's direct-model declaration, keeping its current resolved budget when the suffix is omitted. If the requested target is the previously absent balanced profile, only that requested profile is materialized from the existing balanced resolver's user-derived budget. Unrelated edits do not materialize optional profiles.

For tier and role targets, omitting `@effort` preserves the configured tier budget. An explicit suffix updates the runtime's existing budget field (`EFFORT` or `VARIANT`). For profile targets, an omitted suffix preserves that profile's currently resolved budget. Model identifiers are stored as data and are never executed by a shell. The command does not probe a remote runtime or claim that a saved identifier is available in a particular runtime version.

An invalid target or unsupported budget is rejected before user-file mutation. `--dry-run` and byte-identical no-op requests create no config directory, lock, or backup. A real edit validates the complete candidate, preserves other declarations, comments, ordering, line endings, native settings and unrelated user files, writes one exact preimage backup for an existing config, then atomically publishes the candidate under a canonical target lock. Concurrent invocations of this command serialize. The filesystem's final precheck-to-rename interval is not a kernel compare-and-swap against non-cooperating writers; callers report conflicts they observe and do not roll back a later successor.

The command configures future consumer reads. It does not rewrite generated adapter projections, active route seals, or process-local model selections. Use the existing runtime consumer and route policy as the authority for those surfaces.

## Shipped-default-only maintenance

A change that touches only the shipped default stays separate from the user-owned actual model set: edit `adapters/<harness>/config/models.conf`, then finish through the normal generation and existing fixture path as small `direct` work. It does not pick new concrete default values on its own, does not sync provider or user config, and does not clean up model-name literals across the repo.
